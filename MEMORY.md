## Historical Context & Decisions
*   **Decision 1 (CORS Handling):** Supabase queries route exclusively through the browser's native `fetch()` inside `background.js` — eliminates bundler configuration entirely.
*   **Decision 2 (State Hijacking):** `content.js` uses prototype-based `value` setter override + bubbling `input`/`change` events so React/Vue submission flows accept injected data. Implementation lives in `setNativeValue()` per `agent_docs/tech_stack.md`.
*   **Decision 3 (Hidden Field Protection):** The content-script field finder explicitly skips `type === 'hidden'`, `disabled`, and `readOnly` elements. Verified against the `csrf_token` carrier in `sandbox.html`.
*   **Decision 4 (Popup Stack):** Shipped the client-picker UI as vanilla HTML/JS rather than React+Vite. Avoids a build step under the MVP deadline; React migration is deferred and not blocking Phase 5.
*   **Decision 5 (Field Mapping Coverage):** `FIELD_MAP` in `content.js` resolves each of the 7 client keys (`passport_number`, `surname`, `given_name`, `dob`, `nationality`, `email`, `phone`) against `id`, `name`, `placeholder`, `data-field`, and a composite effective-label string (see Decision 6). Normalization lowercases and collapses every non-`[a-z0-9_]` run into a single `_`, so prompts like "Date of Birth (DD/MM/YYYY) *" still match the `date_of_birth` keyword.
*   **Decision 6 (ARIA & Builder-Style Form Support):** `content.js` now resolves the effective label of an input by unioning `aria-label`, the text of every element referenced by `aria-labelledby`, the nearest ancestor `[role="listitem"]`'s `[role="heading"]` text, and any associated `<label for>`. The candidate selector also includes `[role="textbox"]` and `contenteditable="true"`/`plaintext-only`; contenteditable nodes are filled via `textContent` + bubbled `input`/`change` instead of `setNativeValue`. This covers Google Forms / Microsoft Forms text answers without breaking standard HTML forms. Radio/checkbox widgets were out of scope in this pass and are now handled per **Decision 8**; split date pickers and single-select dropdowns remain deferred (they need bespoke click/option simulation).
*   **Decision 7 (One-Field-One-Match):** `autofillForm` tracks claimed elements in a `Set` so two client keys cannot both write to the same DOM node (e.g., when a vague label like "Name" would substring-match both `surname` and `given_name`). First-key-wins, in `FIELD_MAP` iteration order.
*   **Decision 8 (Choice-Widget Engine — Phase 6):** `content.js` now fills radio groups and checkbox multi-selects via click simulation. `RADIO_FIELD_MAP` (`gender`, `marital_status`, `visa_type`) and `CHECKBOX_FIELD_MAP` (`skills`) resolve a *group* by its label — `[role="radiogroup"]`/`[role="group"]` `aria-label`, the `[role="listitem"]` heading, a `<fieldset><legend>`, or the shared `name` — then match an *option* by its `value`, `data-value`, `aria-label`, wrapping `<label>` text, or `textContent`. Activation uses native `.click()` on the unchecked option (plus bubbled `input`/`change` for ARIA widgets), so React/Vue and Google-Forms `[role="radio"]`/`[role="checkbox"]` widgets both register the selection. The client schema widened from 7 to 25 keys; `mock_clients.js` and the Supabase `clients` table (`supabase_migration_phase6.sql`) mirror the new columns, with `skills` stored as `text[]`. The claimed-`Set` from Decision 7 now spans the text, radio, and checkbox passes so no DOM node is written twice; `findFieldFor` also skips `type=radio/checkbox` so a text key never lands on a choice input.
*   **Decision 9 (Popup Realtime Search Combobox):** The popup's separate `<input type=search>` + native `<select>` pair was replaced by a single combobox (`popup.html` / `popup.js`) — one search input plus a live results `<ul>` rendered beneath it. Root issue fixed: a native `<select>` can't be driven from the search box, so typing only re-populated the OS widget and the analyst still had to open it and pick separately ("dropdown opens but nothing specific gets selected"). `rankedMatches()` scores each client — passport full-prefix (100) > numeric-prefix after stripping country letters e.g. "bd" (90) > in-order passport substring (70) > name (50) > email/phone/nationality/city/occupation (30); ties keep backend order. Matching is in-order substring on the normalized passport, so "998" hits BD9988776 but "899" (same digits, wrong order) matches nothing — the "order matters" requirement. Selection lives in a JS var `selectedClientId` (NOT a hidden input, per EC-01 spirit); matched digits are highlighted via DOM-built `<mark>` (no `innerHTML`); keyboard = arrows / Enter / Escape. Supersedes the Decision 4 "vanilla JS dropdown" description — still vanilla JS, React/Vite still deferred.
*   **Decision 14 (Trusted KEYBOARD via CDP — primary dropdown path):** The trusted *click* (Decision 13) still left dropdowns unselected ("debugger path ran" + `aria-selected="false"`). Two converging insights from the second remediation doc: (1) the documented-reliable path for Google Forms listboxes is keyboard nav (focus trigger → ArrowDown to option → Enter), and (2) synthetic `KeyboardEvent`s are inert because `keyCode`/`which` are read-only and stay `0`, so Google's handler ignores them. The fix marries both with the trusted-event requirement: **trusted keyboard via CDP `Input.dispatchKeyEvent`** — isTrusted AND real virtual key codes — which also needs only the TRIGGER's coordinates (large/stable), sidestepping the narrow option's click box that a non-100%-zoom trusted click likely missed. `background.js` adds `TRUSTED_KEY {key}` → `trustedKey()` (`KEY_DEFS` for ArrowDown/ArrowUp/Enter/Space; rawKeyDown[+char for Space]+keyUp). `content.js` `selectAriaListbox` strategy order is now: **S1** quick synthetic mouse (no banner); **S2** trusted-click the trigger to open+focus, then loop trusted ArrowDown/ArrowUp using `aria-activedescendant`/`aria-selected` feedback (commit with trusted Enter on the active match, or a blind Enter after index-stepping); **S3** trusted click on the option's centre (backup); **S4** synthetic keyboard (DevTools-open fallback). Also fixed synthetic `dispatchKey` to force `keyCode`/`which` via `Object.defineProperty` (the doc-2 read-only fix). Removed the dead synthetic `pointerClick` strategy and the S1 `scrollIntoView` (it could dismiss the popup before S2). OPERATIONAL CAVEATS unchanged: DevTools must be CLOSED (chrome.debugger can't co-attach) and browser zoom should be 100%; banner shows while attached, dropped on `sendDetach`.
*   **Decision 13 (Trusted-Event Bridge via chrome.debugger):** Root cause finally pinned: this Google Forms build gates its dropdown `jsaction` handlers (`UX7yZ` mousedown, `lbsD7e` mouseup, `I481le` keydown) on `event.isTrusted`. A content script's `dispatchEvent` is always `isTrusted:false` and cannot be forged, so *every* synthetic strategy (mouse, keyboard, pointer) fails to commit the selection — confirmed by the keyboard path (layout-independent, dispatched straight to the listbox's own handler) also failing. User chose the trusted-event route. Added the `"debugger"` permission and a CDP Input bridge: `background.js` exposes `TRUSTED_CLICK {x,y}` → `attachDebugger(tabId)` (once; tolerates "already attached" orphan sessions) → `Input.dispatchMouseEvent` mouseMoved/mousePressed/mouseReleased at viewport coords → real trusted click; plus `TRUSTED_DETACH`, an `onDetach`/`tabs.onRemoved` cleanup of the `attachedTabs` Set. `content.js` `selectAriaListbox` now runs: **S1** quick synthetic mouse-commit (no banner for non-gated listboxes), **S2** trusted `trustedClickAt()` — opens the trigger if needed, `pollForSettledLayout`s the option, `scrollIntoView` + recompute rect, trusted-clicks its centre, **S3** synthetic keyboard (used when the debugger can't attach), **S4** synthetic pointer+click. `runJob` calls `sendDetach()` on completion/error (not on `done:false`, so the debugger survives a real navigation for the next page). KEY OPERATIONAL CAVEAT: `chrome.debugger` cannot attach while **DevTools is open** on the tab — the bridge returns an error and the final console warning says exactly that ("close DevTools and retry"). So the trusted path must be tested with DevTools CLOSED; judge success by the dropdown value + popup count, not the console. Trade-off accepted by user: Chrome shows a "Sticker Visa Auto-Filler started debugging this browser" banner while attached (auto-dismissed on `sendDetach`). Native `<select>` (`setNativeSelect`) and all non-dropdown widgets are unaffected.
*   **Decision 12 (Trailing-Click Toggle Bug — the real "did not settle" cause):** A pasted live widget DOM revealed the root cause. The Google Forms listbox (`role="listbox"`, `jscontroller="YwHGTd"`) carries `jsaction="click:cOuCgd(LgbsSe); ... mousedown:UX7yZ(LgbsSe),npT2md(preventDefault=true); mouseup:lbsD7e(...)"`, while each option (`div.MocG8c`, `jsname="wQNmvb"`) has an **empty** `jsaction`. So selection is committed by `mousedown`→`mouseup` **bubbling to the listbox's delegated handlers**, and `click` on the listbox is the open/close **toggle** (`cOuCgd`). Our `pointerClick` fired a trailing `click()` after mousedown/mouseup — which bubbled to `cOuCgd` and closed the listbox before the choice settled, leaving `aria-selected="false"`. Fix: new `mouseCommitOption(el)` fires only the pointer/mouse `down`→`up` pair (no click, no mid-sequence focus) and is now Strategy 1. `keyboardSelectOption` was rewritten to step using live `aria-activedescendant` feedback (re-read each step) instead of a guessed start index, and is Strategy 2. Inner-node mouse-commit is Strategy 3; the full `pointerClick` (with trailing click) is demoted to Strategy 4 (last resort). Each strategy is still gated by `chosen()` (aria-selected/aria-checked on the matched option, or the collapsed trigger's text equalling the value). Open is still a single plain `triggerEl.click()` (Decision 10c). If synthetic events ever prove insufficient on a given portal, the documented fallback (per the remediation guide and common auto-fillers) is to highlight the dropdown for manual selection — not yet implemented.
*   **Decision 11 (Settled-Layout Polling for Dropdown Options):** Per the *Debugging Google Forms Dropdown Extension* remediation guide, `selectAriaListbox` now polls each option for layout settling before any click-based strategy. New helper `pollForSettledLayout(produce, timeoutMs)` re-evaluates a producer via `requestAnimationFrame` and only resolves once the returned element has `rect.width/height > 0`, `display !== 'none'`, `visibility !== 'hidden'`, and `opacity > 0`. Wired into Strategies 2 and 3 (option pointer-click and inner-span pointer-click) — both previously read `getBoundingClientRect` while Google's popup was still mid-animation, dispatching coordinates at a collapsed (`height:0`) target so JSAction silently dropped the click. Added Strategy 4 as a last-ditch keyboard re-cycle after a fresh re-open: when the click strategies fail mid-animation and the listbox auto-resets its `aria-activedescendant`, a clean keyboard walk from a known state still commits. Failure log restated to match the guide ("option clicked but selection did not settle"), and now includes `matchVisible` so the failure mode is unambiguous in the console. Decision 10's open/match/scope logic is untouched; this only hardens the click step.
*   **Decision 10 (Detached Multi-Page Autofill Job + ARIA Dropdown Fix):** Three field-side bugs were fixed for live multi-section Google Forms / real multi-page portals. **(a) "message channel closed before a response was received"** — the `AUTOFILL` listener used to `return true` and hold the channel open for the whole walk; a Next click that navigates tore down the content script before `sendResponse`. Now it acks synchronously (`sendResponse({ ok, started })`, `return false`) and runs the walk **detached**. **(b) "auto-advances but each page needs another click"** — same root cause on real navigations (the new page's fresh content script had no trigger). Fixed by persisting the job (`sva_autofill_job` in `chrome.storage.local`: `{ client, autoAdvance, origin, expiresAt, pagesFilled, maxPages }`) on click and **resuming it on every page load** (`getActiveJob().then(runJob)`). Guards: same-origin only, `maxPages=30`, `TTL=5min`, and `findNextButton` still excludes Submit/Back/Clear so it never submits. `autofillWalk` returns `{ done }`: true = finished / guard-tripped (clear job + report); false = Next clicked but section didn't swap in place (navigation likely in flight — leave the job for the next load to resume). **(c) "dropdown opens but selects nothing"** — root cause: a Google Forms listbox **toggles** on activation, so opening the trigger with the full pointer+`.click()` sequence opened it and immediately closed it again (verified by a double-toggle simulation), so the option click never landed. Fix: `selectAriaListbox` opens the trigger with a **single plain `.click()`** (one retry), **waits for `aria-expanded="true"` / visible options**, scopes options to the listbox (own children, then `aria-controls`/`aria-owns`, then document), skips empty-`data-value` placeholders, matches by `data-value` / `data-answer-value` / `aria-label` / text, then `scrollIntoView`s and clicks the **option** via the `clickElement()` pointer-event helper (a bare `.click()` on a Forms option is ignored). Key asymmetry: `clickElement()` (pointerdown/mousedown/pointerup/mouseup + `.click()`) is used for the **Next button and the option**, but NOT the toggling **listbox trigger**. Logs `expanded` + all candidate `data-value / text` pairs on a miss. Results flow back to the popup via a runtime `AUTOFILL_DONE` message + `sva_autofill_result`. Removed now-dead `autofillAllSections`, `findAriaOption`, `waitForResult`. `FIELD_MAP` / `RADIO_/CHECKBOX_/SELECT_FIELD_MAP` and `isWritable` hidden-field protection untouched.

*   **Decision 15 (Admin CRUD Page — `admin.html`):** Standalone single-file page (not part of the extension bundle) to view/insert/edit/delete the Supabase `clients` table without hand-writing SQL. Self-contained (no module imports, so it runs from `file://`): a connection bar (URL pre-filled, key pasted + persisted to `localStorage`), an auto-generated 25-field add/edit form driven by a `FIELDS` schema array mirroring `FIELD_MAP`, and a live table with per-row Edit/Delete. Talks to PostgREST directly (`GET ?select=*&order=id.asc`, `POST` with `Prefer: return=representation`, `PATCH ?id=eq.N`, `DELETE ?id=eq.N`). Empty inputs are omitted from the payload (so `""` never hits date/int columns); `skills` splits comma → `text[]`; `length_of_stay` → number. KEY CAVEAT surfaced in the UI and on 401/403: the committed anon key is read-only under RLS, so writes need the **service_role** key (local only, never deploy) or a `create policy ... for all to anon` demo write policy. `id`/`created_at` are shown but not editable.
